# 09. UX, UI e identidad

## Principio

Diseñar por tarea, no por una lista de tablas. Una misma plataforma no obliga a
mostrar el mismo panel a todos. Los permisos determinan acciones, y la
experiencia reduce la carga de cada rol sin ser la frontera de seguridad.

| Rol | Inicio y tareas objetivo | Prioridad |
|---|---|---|
| Super Usuario | Comercios, salud de plataforma, planes, accesos, incidencias | Control global, operaciones sensibles claras |
| Administrador | Trabajo pendiente, ingresos conciliados, personal e inventario | Estado de su negocio, no datos globales |
| Asesor | Recepción guiada, búsqueda de cliente, comunicación y entrega | Rapidez y claridad; no permisos financieros implícitos |
| Técnico | Mis asignaciones, diagnóstico, repuestos, actualización | Foco en trabajo y trazabilidad |
| Cliente | Mis equipos, progreso, aprobaciones y comprobantes | Lenguaje sencillo, privacidad y confianza |

Las pantallas actuales son una base funcional a integrar: no son el diseño final
completo de esos cinco productos. El formulario maestro usa UUIDs como bootstrap;
un selector seguro y búsqueda de usuarios reemplazarán esa entrada antes del
piloto. No se deberá exigir al usuario final conocer identificadores técnicos.

## Flujos objetivo

Recepción: elegir comercio -> identificar cliente -> describir equipo/estado y
falla -> anexos consentidos -> revisar -> crear orden -> entregar voucher.
Técnico: ver asignación -> diagnóstico -> cambio permitido -> evidencia ->
notificación. Pago: elegir orden -> registrar importe/medio -> estado pendiente ->
conciliar evidencia real -> step-up MFA -> confirmar -> voucher y saldo correcto.
Cliente: login -> ver solo sus órdenes -> historial -> comprobantes ver/imprimir.

Faltan las aprobaciones de presupuesto, fotos, autorizaciones de backup, entrega,
garantía, cancelación y devolución. Se diseñan antes de extender las pantallas.

## Estados de interfaz

Cubrir cargando, vacío, error, sin permisos, sesión vencida, sin conexión,
conflicto de versión, operación en curso y suscripción suspendida. No mostrar
éxito antes del commit. En timeout financiero, consultar el estado del intento
antes de crear otro pago. Evitar mensajes que revelen que existe el registro
privado de otro negocio.

Ejemplos: "Operación registrada correctamente" después de respuesta confirmada;
"La orden cambió; actualice antes de guardar" ante conflicto; "No hay equipos
asignados" en una bandeja técnica vacía. No culpar al usuario ni prometer que se
envió un WhatsApp cuando no existe una confirmación del proveedor.

## Sistema visual provisional

Tokens CSS en globals.css: tinta, secundario, superficie, fondo, borde, acento,
estado de riesgo y radio. Fuente del sistema, sin descarga de archivos de fuentes.
Fondo claro, contraste alto, tarjetas con jerarquía, formularios etiquetados y
controles de al menos 44 px. Esta paleta es de trabajo y no reproduce un manual
de marca que no se pudo recuperar. No se entrega un logo supuesto como aprobado.

Al integrar el manual: nombre, colores, tipografías licenciadas, logo original,
área de respeto, iconos, piezas y PDF. Versionar tokens, no duplicar hexadecimales
en decenas de pantallas. Figma será la referencia de componentes y flujos;
Git contendrá su implementación y contratos.

## Accesibilidad y móvil

Objetivo WCAG 2.2 AA; validar contraste, foco visible, navegación con teclado,
labels, errores asociados al campo, lectura de estados y ampliación. No depender
del color para diferenciar estados. Evaluar accesibilidad del QR MFA y alternativa
manual de configuración antes del piloto. La auditoría completa no está realizada.

La PWA se implementará primero como instalable con shell seguro. No cachear pagos,
comprobantes o datos de clientes en dispositivos compartidos. Escrituras offline,
reconciliación y conflictos requieren otro diseño; instalar una PWA no equivale a
soportar operaciones offline correctas.

## Validación de usabilidad

Probar con representantes de recepción, técnicos, administración y clientes:
tiempo para recibir una orden, errores de entrada, comprensión de estado y
capacidad para obtener ambos comprobantes. Documentar hallazgos, cambios y retest.
La maqueta offline adjunta solo permite explorar composición y roles con datos
sintéticos; no demuestra implementación de funciones de negocio.
